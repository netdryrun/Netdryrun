# Changelog

## Unreleased

### Fixed

- **FRR 10.2: `record` and route checks stopped on every BGP prefix answer** (found by the synthetic stranger on
  published 0.4.1, with martimy/clab-bgp-frr). FRR 10.2.1 lists a prefix's BGP paths in `show bgp ... <prefix> json`
  but leaves out `pathCount`, which 0.4.1 required as its check that no path was dropped, so `record` reported every
  leaf's own-LAN guard as an INCOMPLETE BASELINE.
  - Where `pathCount` is missing, the count now comes from the text answer of the same command ("Paths: (N available").
  - A count that doesn't match the paths listed is still an error, and a text answer without one is a named gap.
  - An answer without its paths is never read as "absent".

  Oracle `tests/oracles/FP-042-FRR102`, from a live FRR 10.2.1 capture.
- **`record` on BGP-unnumbered links:** every fabric link was an INCOMPLETE BASELINE "no global address" gap, 12 of the
  18 the stranger hit on martimy/clab-bgp-frr.
  - An interface is now named "BGP unnumbered", with no subnet to guard, only when two things hold: it lists
    link-local addresses only, and the node has a BGP session over that interface.
  - Everything else stays a gap: no such session, an interface whose addresses can't be read, or no driver.
  - An address token that can't be parsed is now an error instead of being dropped, so a global address can't read as
    "none".

  Oracle `tests/oracles/FP-042-UNNUMBERED`, from the same capture.
- **Own-address reads skipped text before the JSON** (found by ClusterFuzzLite on the 0.4.2 work). Since 0.4.1 every
  driver's own-address reader (the ping check's own-target and source guards) started at the first `{` or `[`, so an
  answer with a CLI error line or other text in front of its JSON read as a shorter address list, often an empty one.
  The answer must now be the JSON document, with only whitespace around it; anything else is unexpected output.

  Oracle `tests/oracles/FP-042-ADDRLOAD`, from the fuzzer's saved crash input.
- **SR Linux on containerlab 0.83: every check was refused** as "in the namespace of ..., which is not a lab node"
  (found by the synthetic stranger; `netdryrun run examples/srl-frr` exited 2). containerlab 0.83 runs an SR Linux node
  in a namespace holder container it makes for that node.
  - That holder now counts as the node's own namespace, but only when it carries containerlab's labels for this lab and
    this node (`containerlab`, `clab-internal-node: "true"`, `clab-root-node-name`), Docker finds it under the name or
    id the node's network mode gives, and it holds its own namespace.
  - Its Docker networks are the node's management networks, so a ping over them is still refused.
  - Still refused: network-mode host, a holder for another lab or node, a container with the holder's name but not
    its labels, and a holder Docker can't read.

  Oracle `tests/oracles/FP-042-SRLNETNS`, from a containerlab 0.83.0 capture.
- **`record --attributes` on SR Linux left out an AS path it couldn't read, without a warning** (case 4 of the 0.4.1
  advisory, GHSA-ggcf-664f-c9ff; a regression in 0.4.1). SR Linux prints no as-path container for an empty AS path
  (an iBGP peer's own route), and nothing in its answer tells that from a missing one. So the recorded check passed
  once the path changed.
  - Where the best path's AS path can't be read, on any driver, `record` now writes no `bgp_route` check for that
    route. An INCOMPLETE BASELINE line names it, so `record` exits 1.
  - A local preference the driver can't read is named in a warning, not dropped silently.

  Oracle `tests/oracles/FP-042-RTS01` (red-team finding RT-S01), from a live SR Linux 26.7.2 and FRR 10.4.1 capture.

### Changed

- **`record --attributes` on SR Linux: a route its iBGP peer originates now gets a named gap instead of a check.**
  0.4.1 wrote a `bgp_route` check for it without `as_path`, which passed a changed path. 0.4.2 writes no check for that
  route, and an INCOMPLETE BASELINE line names it, so `record` exits 1 where it exited 0. Add the check by hand once
  SR Linux's own report shows the path (`as_path: ""` for an empty one). eBGP paths, and every FRR path, are recorded
  as before, with their AS path, and `record` still exits 0 on them.

## 0.4.1 (2026-11-09)

Released without the scripted acceptance run on the final candidate (owner decision, 2026-11-09): every other
layer of the release gate passed on the tested code, and 0.4.1 fixes the published false passes of 0.3.3 and 0.4.0.
The record is in `releases/0.4.1/review.md`.

### Added

- **Capture kit: `netdryrun capture` and `netdryrun sanitize`.** Contribute your NOS version's output without sharing an image. `capture` runs a driver's own read commands on one node of a running containerlab lab, recorded as the driver sends them, and writes a bundle (outputs plus `manifest.json`: NOS, the version the node reports and the one you give, image and digest when Docker has one, scenario, every command with its sha256). It refuses any other target before running anything: a node not in the topology, an address or hostname, a `host` or `ext-container` node, or a container whose containerlab labels don't name this lab and node. `sanitize` rewrites addresses (IPv4 into 10.0.0.0/8 per /16, IPv6 into 3fff::/20 per /32, prefix lengths, order and containment kept), AS numbers where the output says they are ones, hostnames and secrets, the same way across the bundle, and shows the changes; it writes only with `--confirm`, and only when its self-check passes (no public address or AS number left, structure unchanged, and the driver reads the sanitised outputs as the sanitised version of what it read). The mapping is written outside the bundle. Reference: [capture kit](https://netdryrun.com/reference/capture/).
- **Contributor gates on every pull request** (`.github/workflows/contrib.yml`, `pull_request` only, no secrets): every commit signed off (DCO); the AI-use disclosure ticked; the known-false-pass tests (`tests/known_false_passes.yml`) run as the base branch has them against the pull request's code; a change to verdict code needs a test that fails on the base branch's code; every file in `tests/fixtures` has a recorded source (`tests/fixtures/SOURCES.yml`) and every capture bundle validates; pre-registered corpus cases, their committed results and the nondeterministic list change only with a new AMENDMENTS.md entry; lab templates have a broken variant. With the `run-labs` label, lab templates run good and bad and both corpora rerun, failing on any changed verdict.
- **How the project is run**, in the open: a docs page, an AI-use section in CONTRIBUTING with a disclosure checkbox, CODEOWNERS, a pull request template, issue forms for wrong verdicts ("make it lie"), capture submissions and lab templates, and the lab-template format (`community/labs/`).

### Changed

- **An `only` entry with host bits is a config error** (breaking). `only: [10.1.1.77/24]` was read as `10.1.1.0/24`, which
  widened the allow-list without a word; write the network itself. `route` and `bgp_route` prefixes keep their documented
  normalisation: they name one prefix and widen nothing.
- **Convergence warnings are their own field.** A warning the BGP gate gives (a session still down on another node, prefix
  counts still moving at the cap, a node with no BGP neighbors) is a structured `warnings` list on each check
  (`{code, node, session, text}`) and a top-level `warnings` count and list in the JSON report and the MCP result; the
  console, the summary line and the Markdown summary the Action posts show it too. It is no longer text inside `detail`,
  where the MCP result's 300-character cut could drop it. A warning never changes a verdict.

### Fixes from the 0.4.1 red team (2026-11-05)

Nine false passes found by the red team before release, each fixed with a test on live captured output that fails on the
code before the fix:

- **The BGP gate waits for every routing node, not only the check's own** (B-9005, narrowed). A leak guard on r1 passed
  while r2's session to r3 was still coming up; the leak arrived later. The gate now also waits, up to the same cap, for
  every lab node with a routing driver, in the default VRF and every VRF the checks name. A session still down there at
  the cap, counts still moving or BGP state that can't be read is a warning on every post-convergence check (not a block:
  the check's own node still blocks as before). A session declared down is excluded at both ends. The residual limit is
  in the [trust page](https://netdryrun.com/trust/).
- **End-of-RIB: a table still arriving is not converged** (R3). A session can be established with counts that hold still
  for two samples while the peer is still sending its table (a graceful restart, a slow link). Each driver now reads
  End-of-RIB per family (FRR and SONiC, SR Linux, Arista EOS, RouterOS, Junos, and Cisco NX-OS from its neighbor text);
  the gate waits for it, and at the cap a family still pending blocks the node's post-convergence checks. A peer that
  never sends End-of-RIB is declared with `nodes.<node>.peers.<address>.eor: not_sent`. A session without graceful
  restart negotiated can't be tracked: it settles by stable counts, with one warning per run.
- **Juniper: a graceful-restart stale route is not active** (R4). Junos marks it only in `bgp-rt-flag` (`Stale Accepted`)
  while `rt-entry-state` still reads `Active Ext` (live capture); the driver read `rt-entry-state` alone, so `route` and
  `bgp_route` passed on a route the restarting peer may never re-send. Both are read on every path read; a kept BGP entry
  without the flag is an error. The table-level `restart-state` Junos prints when graceful restart is configured is now
  read (only `Complete` is settled); before, it made every route read on such a router an error. Every driver refuses a
  path carrying LLGR_STALE (65535:6).
- **`link_down` must name a lab link** (B-9001). `link_down` on the management `eth0` took nothing the checks depend on
  down, and every scenario check passed. The interface must be an endpoint of a link in the topology on that node
  (refused before deploying, naming the node's link interfaces); after the fault the interface must be administratively
  down, or the scenario is an error. Every VM kind is refused for link faults.
- **A VRF that doesn't route has no "absent" routes** (R5, A-0049, A-0050). Arista EOS answers a VRF with routing disabled
  (or the default VRF after `no ip routing`) with an empty table, so `present: false` passed; `routingDisabled` is now read
  on every route answer (IPv4 and IPv6) and refused. A disabled SR Linux network-instance is not settled (retried, then
  failed), never "no routes".
- **A ping that never leaves the node is refused** (B-9006). An unspecified, loopback, multicast or limited-broadcast
  target, or one equal to `source`, is a config error; at run time a target that is one of the node's own addresses (or a
  subnet broadcast) fails the check, read per driver. Output that can't be read is retried, never "not own".
- **An `as_path_regex` that matches every AS path is refused** (B-9007). A stray `|` matched the empty string, so the check
  asserted nothing. A pattern that matches every learned probe path (`.+` and `\d` too) is a config error; `^$` stays valid.
- **An `only` entry with host bits is refused** (B-9004; see Changed).

### Fixes from the 0.4.1 candidate's red team (2026-11-08)

Two isolated attackers and a fresh verifier on the final candidate; each class closed on every driver, each case a
test that failed on the candidate (`tests/test_redteam_angle5_d87.py`, RT-0044 to RT-0052). All were in 0.4.0 as well
([advisory](advisories/0.4.0-further-false-passes/), cases 18 to 23).

- **OSPF and RIP names follow the prefix's family on every driver** (RT-0044, RT-0045). An OSPFv3 route carrying IPv4
  (RFC 5838) was reported as `ospf6` on Junos, SR Linux, EOS and NX-OS, a name validate refuses for IPv4, so
  `protocol: ospf present: false` passed with the route installed. OSPF of any version is now `ospf` on IPv4 and `ospf6`
  on IPv6 (likewise `rip`/`ripng`), in one place for every driver; the detail keeps the device's own name.
- **RouterOS: `bgp_route present: false` sees the node's own advertised prefix** (RT-0051): RouterOS lists it only as
  `bgp-output` rows, one per peer, which the driver didn't read. **SR Linux and Juniper: accepted as a documented limit
  for 0.4.1** (RT-0048, owner decision): `bgp_route present: false` doesn't see a prefix the node itself originates and
  exports (SR Linux lists its own routes whether exported or not, Junos lists none); the check's pass says so. Mitigation: guard the prefix on the
  neighbor that would receive it. A fail-closed rule was tried and reverted: it failed the shipped leak guards on a node
  with its own static default. 0.4.2 reads the adj-rib-out.
- **Repeated YAML merge keys are errors** (RT-0050). Two `<<` keys in one mapping, or merge sources sharing a key, kept
  one value silently and could drop a guard.
- **`record --attributes` forbids the well-known communities a path doesn't carry** (RT-0052), where the driver can read
  communities; elsewhere the recorded file says what isn't pinned.
- **Every zebra failure flag takes a route out of forwarding; SONiC needs `offloaded`** (RT-0046, RT-0047). `failed`,
  `offloadFailed`, `queued` and (for BGP and static routes) `trapped`, read by one function for the `route` check and
  `verify`; `verify` waits while an install is queued. On SONiC a BGP or static route is active only with
  `offloaded: true` (sonic-vs printed it even with orchagent stopped: pair such checks with a `ping`).
- **FRR community aliases** (RT-0049): a community check reads the node's `bgp community alias` lines; on a node with
  any alias, no printed community can be trusted (an alias can look like any community, with leading zeros or a
  well-known name), so a community check there fails whenever the path carries any community.

- **`record` exits 1 when the baseline misses a routing node** (acceptance on the candidate). A node whose state
  couldn't be read, with no driver, or still booting was left out with a warning and `record` exited 0, so a change on
  it passed the recorded baseline (SR Linux: a read error on paths both looped and rejected, now fixed; Junos: the VM
  still booting at the 45 s wait). The file is still written, starting with `BASELINE MISSES A NODE`. `record --deploy`
  now waits for VM nodes to answer before its `--wait`, and `--driver NODE=DRIVER` records a beta NOS. Any other
  gap (an `INCOMPLETE BASELINE` line other than the two size caps) also exits 1; a node no driver recognises counts as
  missing unless it is a bridge or a plain Linux host, and so does one answering "no BGP instance" unless named with
  `--no-bgp`.
- **Arista EOS: a `route` check on a node without BGP** (found live on the candidate). cEOS answers every BGP read there
  with `{"errors": ["BGP inactive"]}` (rc 1), which made every `route` check on such a node an error. That exact
  answer now means "no BGP on the node"; any other failure stays an error.
- **SR Linux: paths both looped and rejected no longer break the BGP read** (acceptance on the candidate). An import
  policy that rejects AS-looped paths made "2 invalid routes but a count of 1" an error on every BGP read of the node;
  such paths may already be in rejected-routes, so the count is a range from 0.

### Known limits: four known false passes in 0.4.1 and earlier (red team on the final candidate, 2026-11-09)

Two isolated attackers and a fresh verifier on `26380cb` found four checks that can pass without testing what the
file says, each in one specific setup. They were found offline (the code and the NOS's captured output) and are
published conservatively: none has been reproduced in a Netdryrun lab run yet. Three were in earlier versions; the `record` one is new in 0.4.1, a regression from 45f63df (0.4.0 pinned such a
path as the empty AS path `""`). 0.4.1 ships with them published as
known limits (decision for the owner: no source change after the final gate runs), and the fix is planned for 0.4.2.
Each has a workaround that catches it today:

- **Arista EOS** (RT-0056, RT-0063): `route` with a protocol other than `bgp` and `present: false` doesn't see a
  route of that protocol that EOS didn't select (`show ip route` lists only the selected one). Check it where the
  route comes from, and add a positive check on the selected route.
- **SR Linux EVPN** (RT-0058): `bgp_route present: false` in an ip-vrf without its own `protocols bgp` doesn't see
  imported type-5 routes. Use `route` with `protocol: bgp` and `present: false` in that VRF.
- **FRR and SONiC** (RT-0053): a `ping` in a VRF to an address on the VRF device itself isn't refused as the node's
  own. Put VRF loopbacks on an enslaved interface, or ping the address from another node.
- **SR Linux `record --attributes`** (regression in 0.4.1): an AS path the driver can't read is left out without a
  warning. Add `as_path` to those checks by hand, or review recorded SR Linux baselines for a missing `as_path`.
- **Docs:** `bgp_prefixes` without `afi` counts IPv4 unicast only, also on an IPv4 session that carries IPv6.

### Fixes from the second 0.4.1 red team and audit (2026-11-06)

Each fixed with a test that fails on the code before the fix (`tests/test_redteam_fixes_041_round4.py`,
`tests/test_mgmt.py`):

- **A ping with no lab route no longer passes over Docker's management network** (B3, a false pass in every released
  version; [advisory](advisories/0.4.0-further-false-passes/) cases 16 and 17). Docker gives every Linux container a
  default route over eth0, and containerlab's cEOS config adds one over Management0: with the lab's route gone, the
  ping left through it and anything the Docker host reaches answered; `route 0.0.0.0/0` without `protocol:` passed on
  it too. After `setup:` and before the first check, Netdryrun now deletes exactly that route (Linux and SONiC nodes in
  the node, cEOS in its config; logged per node in the report's `environment.nodes.<node>.management_default`). Any
  other route over a management interface, a route that comes back (checked before and after every FRR, SONiC and cEOS ping, and
  around each phase and scenario), a ping target or source in the management network, a check on a node in the Docker
  host's namespace, or routes that can't be read end the run as an error (exit 2). Internet access from lab nodes now
  works only during `setup:`. A ping `source` must be one of the node's own addresses. A Junos (cJunosEvolved) or cEOS
  node whose CLI isn't answering yet after `setup:` gets up to 300 s (the setup budget, on the clock) for this first
  read; one that never answers is an error (exit 2) naming the node and the last error (live 2026-11-08: a
  cJunosEvolved still booting).

- **A RouterOS peer's End-of-RIB isn't waited for** (live 2026-11-08). RouterOS 7.x never sends End-of-RIB (it receives
  it), so a neighbor's End-of-RIB from a RouterOS node stayed pending and the gate waited out its cap: the mikrotik
  example took about 11 minutes instead of 2. Where the topology places the peer on a link to a RouterOS node in the lab
  that owns the neighbor address, a pending End-of-RIB from it is judged by stable prefix counts, with one warning
  naming it, as for a session without graceful restart. A RouterOS peer that can't be placed is still waited for. The RouterOS driver also reads vrnetlab's health file up
  to three times, 2 s apart, when it is empty (vrnetlab rewriting it), before reading the router as not ready.

- **Every own address a ping can't leave the node for is read** (RT-0044, RT-0045, RT-0046, RT-0047). Cisco NX-OS read
  IPv4 primaries only, so a ping to the node's own IPv6 or secondary address passed; it now reads `show ip interface vrf
  all` and `show ipv6 interface vrf all` (live capture), with masks, so a subnet broadcast is refused there too. An
  Arista EOS `ip address virtual` (and its secondaries) is the node's own. The IPv6 subnet-router anycast address of an
  own prefix is refused on every driver. Each driver declares the address families its read covers; a target of
  another family is not evaluated, never passed.
- **The gate doesn't give up on a ping-only node at its first failed read** (B2). Any failed read other than "no BGP
  instance" is an unready sample, retried up to the cap.
- **A node the file says runs BGP whose state is never readable is not evaluated** (B1). Its post-convergence checks
  fail as not evaluated at the cap, every sample unready; before, they ran without the gate. On a node with no BGP
  check they run with a `gate-unreadable` warning.
- **A family whose End-of-RIB isn't tracked is said so.** A session carrying routes in a family its End-of-RIB read
  doesn't list (graceful restart not negotiated for that family) settles by stable counts with the once-per-run
  `eor-untracked` warning, instead of silently.
- **Address output of another shape is an error, never "no addresses".** The own-address parsers (FRR and SONiC `ip -j
  addr`, Arista EOS, SR Linux, Cisco NX-OS) refuse entries they don't know.
- **JUnit reports carry the convergence warnings** in each testcase's `<system-out>`; the status is unchanged.

Eight false passes are fixed: one in `record` (0.3.3 and 0.4.0, the [advisory](advisories/)) and seven found by the weekly adversarial run on 2026-11-01 (RT-0021 to RT-0027 in `tests/redteam/`). 0.3.3 and 0.4.0 will be yanked from PyPI.

- **`record` no longer lets a small leak pass** (found by our end-to-end test, the synthetic stranger, on 2026-10-31; [example](examples/frr-customer-leak)). From 0.3.3 it recorded each neighbor's prefix count as a range, today's count up to 20% more (at least 2): a change that let one foreign prefix through a customer's broken inbound filter stayed in range, and `netdryrun run` exited 0. Now each eBGP neighbor's `bgp_prefixes` check also lists the prefixes it sends today under the new key `only`, and any other prefix from it fails, even within the range or replacing a listed one. iBGP neighbors keep the range alone. `only` is read on FRR and SONiC (`show bgp <afi> unicast neighbors <address> routes json`, captured on FRR 10.4.1); on the other drivers, and for a neighbor with more than 500 prefixes, `record` writes the exact count instead and a warning in the file (a change that replaces a prefix still passes there). A baseline recorded with 0.3.3 or 0.4.0 has no `only` lists: record it again. Trade-off: growth you expect from an eBGP neighbor (a customer's new block) now fails the recorded file until you add the prefix to `only`.
- **FRR: a route zebra selected but failed to install is not present** (RT-0021). zebra leaves `installed` out when a route isn't in the FIB (and prints `failed: true` when the install failed); the driver read a missing key as installed, so `route` passed. Now only `installed: true` without `failed` counts.
- **Every well-known community name FRR prints is its number** (RT-0022, RT-0027): `internet` (0:0), `accept-own-nexthop` (65535:8), `route-filter-translated-v4`, `route-filter-v4`, `route-filter-translated-v6` and `route-filter-v6` (65535:2 to 65535:5) were kept as text, so `without_communities` never matched them and passed. These names are now accepted in `netdryrun.yml` too. And `without_communities` fails on a path that carries a community printed by a name Netdryrun can't turn into a number (a `bgp community alias`, a name it doesn't know): it could be one of the listed ones.
- **SR Linux: `protocol: bgp-evpn` matches EVPN routes** (RT-0023). The driver read every BGP route type as `bgp`, so `bgp-evpn` matched nothing and `present: false` always passed. `bgp-evpn` and `bgp-vpn` routes now keep their names; `protocol: bgp` still matches them.
- **A route protocol the node's driver never reports is refused before the lab deploys** (RT-0024). `protocol: bgp-evpn` on an FRR node (zebra reports EVPN routes as `bgp`) was accepted and matched nothing; so was any name outside a driver's set. Each driver now declares the names it can report, and `validate` and `run` refuse the others (exit `2`); the sets are in the [protocol names](https://netdryrun.com/reference/config/#protocol-names) table.
- **Arista EOS: OSPFv3 routes are `ospf6`** (RT-0025). The protocol map had no entry giving `ospf6`, so `protocol: ospf6 present: false` passed with an OSPFv3 route installed. Every OSPF route type in an IPv6 table is now `ospf6`, and every OSPF route type (NSSA included) in an IPv4 table is `ospf`.
- **Arista EOS: a route the node couldn't program is not active.** A routing-table entry with `kernelProgrammed: false` or `hardwareProgrammed: false` (a full TCAM, say) does not forward, but `route` passed on it. It now reads as present and not selected, so `present` fails and `present: false` still fails (found by the 2026-11-01 adversarial run; cEOS 4.36.3M prints both flags on every route, and a false one was not seen in a lab).
- **Arista EOS: `GSHUT` is graceful-shutdown (65535:0).** EOS lists that community as `GSHUT` (cEOS 4.36.3M capture); it was kept as a name, so `communities: [graceful-shutdown]` failed on a path that carried it and `record` wrote `gshut`, which `validate` refused. Not a false pass: `without_communities` already failed on the unknown name.
- **`verify`: `with:` on `appears_on` explains only the paths it pins** (acceptance round, 2026-11-02; RT-0035). Once the best path matched the pins, the line explained every new path for the prefix, so a change that also opened a transit peer's inbound filter (a second, non-best path from that peer with a hijacker's origin AS, best as soon as the customer session drops) got INTENT MATCHED. Now the line explains the paths and received routes from a neighbor whose route matches every BGP pin, and any other new path for the prefix is undeclared. An intent that relied on the old reading now fails: declare the second path or remove it. The reference also no longer says a "not tested" config line changed nothing the lab could observe: verify lists every changed line on a declared node, exercised or not.
- **`record`: a session that is down is an INCOMPLETE BASELINE** (acceptance round, 2026-11-02). It has nothing to record, so a change to it goes unnoticed; that was one warning among the others, and is now an `INCOMPLETE BASELINE` line first in the file and on stderr, like the other gaps.
- **`inject_routes`: a scenario whose routes never left the injecting node is inconclusive** (acceptance round, 2026-11-02). The scenario BGP gate waits for prefix counts to stop changing, which counts that never changed do at once, so with an outbound filter on the injecting node (or no session carrying the family) a `max:` or `present: false` check elsewhere passed on nothing. Netdryrun now waits, before the scenario's checks, until the injecting node advertises every injected prefix to each BGP peer (its adj-rib-out after outbound policy, read as strictly as `verify` reads it), and a peer counts as reached only if its session was established in the prefix's family when the routes went in, was advertised every prefix before the checks ran, still is after them, and never reset in between. Every peer and every prefix: the routes reaching one neighbor says nothing about another's side (Layer 6 review), and a count can't say which prefixes left (round 3). A prefix-limit reset proves nothing (round 5). If a peer wasn't reached, every check in the scenario that passed is not passed, naming the peer and the prefixes ("inconclusive: the injected routes on <node> did not all reach its BGP peers: <address> was not sent <prefixes>", or "never left <node>: no established <family> BGP session there carries <prefixes>"); a check that failed anyway stays failed (exit `1`); otherwise the run exits `3`. A filter further along the path still passes as before: the routes left. The reference no longer overstates the gate either. It also says that one containerlab lab at a time per host is supported (two simultaneous deploys can collide on the management network; Netdryrun exits `2` with containerlab's error).
- **`bgp_prefixes`: a family the session doesn't carry is never counted as 0** (acceptance round, 2026-11-02). It counted 0, so any `max` passed on it. ### Added

- **`netdryrun verify` (0.4, FRR only).** The verdict an agent gets without writing checks: declare what a change is meant to do, and every other difference in the network's behavior fails. `netdryrun verify topology.clab.yml --before <dir|git-ref> --after <dir|git-ref> --intent intent.yml [--json report.json]` deploys the lab with each side (the topology must be identical on both sides, or exit code `2`), takes a snapshot once two full snapshots `--settle` seconds apart are identical, and matches the diff against the intent.
  - **Sides**: each side is built as a whole, isolated tree (the repository tree at a git ref, or the whole directory), and every bind is resolved inside it (`..`, `~`, `${VAR}`, symlinks); a bind that resolves outside the side's tree, or a bound file left out by `export-ignore`, is exit code `2`. Before booting, verify hashes every bound file per side, prints which differ, and stops if the sides collapsed into one ("both sides resolved to the same configs"). Reference: [verify](https://netdryrun.com/reference/verify/).
  - **The snapshot**: BGP sessions (compared as established or not, with soft-reconfiguration per address family; the raw FSM state is evidence only); the VRFs of each node; routes of every protocol with selected versus received-only, FIB-installed, next hops and their resolution, distance and metric; every BGP path per prefix (source, AS path with AS_SEQUENCE order kept and AS_SET as a sorted set, origin, next hop, local preference, MED, weight, standard, extended and large communities in one canonical form, cluster list, originator ID); the Adj-RIB-Out of every established session, including neighbors outside the lab; and received routes before inbound policy where `soft-reconfiguration inbound` keeps them. Keys include VRF, AFI and SAFI. FRR output is validated strictly: an unknown or missing field, a VRF missing from one output, an unsupported address family or an unnumbered neighbor is exit code `2`, never a smaller snapshot.
  - **The intent language**: `appears_on` (selected and FIB-installed by default; `with:` pins the source, next hop, AS path and more), `disappears_from` (selected before; `including_received_only` for received-only routes), `best_path_on` with `to:` (listed values exact, everything else frozen), `session ... goes: down` with a required `afi:` (covers only the routes learned over that session, both ends; a neighbor deleted from the config is a separate `session removed` difference), `advertisement` (one node's advertisement to one neighbor, for outbound changes toward peers outside the lab; `goes: added` carries the node's best path, or the values in `with:`), and `allow_anywhere` (exact prefixes, or globs where `*` is one whole octet or hextet, with an explicit length and at most /16 (/48) of reach; every route an entry explained is listed; never supernet containment; a warning in every report that uses it). The whole intent is validated before any lab boots.
  - **Verdicts**: `INTENT MATCHED`, `NO BEHAVIOR CHANGE` (empty diff, empty intent), `UNDECLARED CHANGES: DO NOT APPLY` (an undeclared difference, a declared change that didn't happen, or a failed standing guard), `INCONCLUSIVE` (exit code `3`; retry at most once, then escalate), and an unhealthy baseline (sessions down before the change; `--allow-unhealthy-baseline` to go on). `verify` never prints `SAFE TO PROCEED`, and every report echoes the intent at the top: explained is not the same as safe.
  - **Standing guards**: the checks of a `netdryrun.yml` run on the after lab, and they must pass. With a git ref as `--before`, they are read from that ref, never from the change: the `--guards` path, or by default the `netdryrun.yml` next to the topology there. With a directory as `--before`, only an explicit `--guards`. The report says `guards_source`, and a verdict without guards says "no standing guards ran". An intent file that the change itself edits is flagged for a code-owner review.
  - **No approval from a single boot.** When the verdict would approve (`INTENT MATCHED`, `NO BEHAVIOR CHANGE`), each side boots a second time and must give the same snapshot; if one doesn't, the verdict is `INCONCLUSIVE`, listing every item that differed (`determinism` in the report). So an approval takes four boots.
  - **From the cold review (`releases/0.4.0/review.md`):** a side that is both a directory and a git ref is exit 2 (a pull request could add a folder named like the base commit); the two ends of a session pair within a VRF and never ambiguously; a new advertisement's next hop must be the best path's or the node's own unless pinned; `goes: down` explains a session only when nothing but its state changed; an empty advertised listing for a session that sent prefixes is a failed read.
  - **No route ceiling.** The snapshot holds every route; a command that never finishes within the timeout cuts it, and the verdict is `INCONCLUSIVE` naming that command.
  - **What two boots of the same configs differ in is not compared:** the management address on `eth0`, the random IPv6 link-local addresses (a link-local next hop is named by the lab node and interface that own it; one no lab node owns keeps its address, so a typo in a configured one is a difference: 0.4 gauntlet) and which `fe80::/64` zebra marks selected. Found by running `verify` live on a comment-only change.
  - **Read from live FRR 10.4.1 output** (the test fixtures are live captures, `scripts/capture_verify_fixtures.py`): received routes come from the plain `received-routes json`, because the detail listing prints the path after inbound policy; a default route sent by `default-originate` (listed outside `advertisedRoutes`) is an advertisement; aggregate and route-reflector-client path flags are compared.
  - **The report** `netdryrun.verify/v1`, with a published JSON Schema ([`verify-v1.json`](https://netdryrun.com/schemas/verify-v1.json)): every undeclared item with a `next_diagnostic` command for its node, every declared change that didn't happen, what each intent line explained, the guards, and both snapshots with the raw output of every command as evidence.
- **The MCP tool `verify_change(topology, before, after, intent, guards=None)`**, on the same engine. `intent` is the intent as YAML or JSON text, or the path of an intent file; the report records `intent_source: "mcp"`. The result is typed: `$defs/verify_result` in [`mcp-result-v1.json`](https://netdryrun.com/schemas/mcp-result-v1.json), with its own frozen verdict enum (the `netdryrun.verify/v1` verdicts), the echoed intent, up to 50 undeclared items with their `next_diagnostic` (`undeclared_total` counts all), what didn't happen, the guards, and `evidence_file` (the full report, written as `netdryrun-verify-report.json` next to the topology, never through a planted symlink). `NETDRYRUN_MCP_ROOT` applies to the topology, directory sides, the intent file and the guards. The description says the verdict is `INTENT MATCHED`, `UNDECLARED CHANGES: DO NOT APPLY` or `INCONCLUSIVE`, that it never prints `SAFE TO PROCEED`, that the intent comes from the ticket or the operator and is never widened to make a change pass, and that it takes two lab boots (about 2–4 minutes).
- **The GitHub Action's `mode: verify`.** It compares the base branch with the pull request merged into it (GitHub's merge commit), so what lands is what is booted. A job is green only on exit `0` with an approving verdict. New inputs `mode` (`run` by default, or `verify`), `topology`, `intent-file` (default `netdryrun-intent.yml`) and `allow-intent-edit`, and a new `verdict` output in both modes. Before is the base branch tip, after the PR's merge commit; the standing guards are the base branch's `netdryrun.yml`. **A PR that adds or edits the intent file fails** before any lab boots ("intent edited in this PR: requires a code-owner approval"), unless `allow-intent-edit: true`, which a workflow should set only where branch protection requires a code-owner review of that file; `CODEOWNERS` should list the intent file and `netdryrun.yml`. The PR comment (the existing `pr-comment` mechanism) and the job summary show the verdict, the echoed intent, the undeclared items and their next diagnostics. Stale reports are deleted before the run, and the outputs come from this run's report only (status, verdict and exit code must agree), one line, sanitised. Reference: [GitHub Action](https://netdryrun.com/github-action/#verify-a-change-against-its-intent-mode-verify).
- **Nodes verify can't snapshot are refused or named.** A node on any platform but FRR (SR Linux, SONiC, Arista EOS, Juniper) is refused before a lab boots, naming `--unobserved` and its cost; run as `--unobserved`, it is stated in every output (changes on it are not compared). The Action's new `timeout` input passes `--timeout` in `mode: verify`, for labs with a slow-booting node; with the default, a node still booting gives exit code `3`, never an approval.
- `netdryrun verify --markdown FILE` writes that summary (lab text made inert, as in the run report), and `--intent-source` (`cli` or `action`) records who supplied the intent.
- `AGENTS.md`, the agent skill and every MCP tool description now say: when no checks exist and a ticket states the intent, prefer `verify_change`.
- **A machine-readable capability statement**, [`capabilities.json`](https://netdryrun.com/capabilities.json): the use cases with MCP, CLI and Action invocation examples, the prerequisites, the limits, the platforms, tools, check types, verdicts and exit codes, in one file generated from the source (`scripts/capabilities.py`; `sync_facts.py --check` fails when it is stale). It is referenced from `server.json` (`_meta`), `AGENTS.md`, `llms.txt`, the AI agents page and the MCP server's instructions.

### Fixes

- **False approvals found by the 0.4 expert gauntlet** (outside experts played by AI models, and a code-reading agent; each pinned by a test in `tests/test_verify_gauntlet.py`):
  - **No bound file differs: nothing to verify** (exit `2`, before any boot). A change to a file the lab doesn't bind used to approve as NO BEHAVIOR CHANGE after four boots.
  - **Only an observed node's FRR config may differ.** A changed `daemons` file (shell FRR's start script runs), `vtysh.conf`, a script or the config of an unobserved node can change what runs unseen: exit `2`, naming the file.
  - **`--unobserved` refuses an FRR router**: it would leave any change on it uncompared.
  - **`appears_on` never accepts a discard route.** A route whose every next hop drops traffic (`ip route X Null0` plus `redistribute static`) satisfied "selected and in the FIB", and so did a BGP route whose next hop resolves over a discard route; such a route is now `state: discard`, declared as such.
  - **A link-local next hop set in config is compared.** Every IPv6 link-local next hop was compared as `fe80::`, so a typo in a configured one was invisible. It is now named by the lab interface that owns it (stable across boots), and one no lab node owns keeps its address.
  - **The Action refuses a PR that edits the workflow judging it** (`mode: verify`: any change under `.github/workflows/` or `.github/actions/`; `mode: run`: such a change together with anything else, since the PR could point `path` at a lab it didn't touch). Under `pull_request` the workflow comes from the PR, so it could set `allow-intent-edit` for itself.
- **A missing MED never reads as MED 0** (0.4 interop test, live Junos, cEOS, SR Linux and FRR in one lab; tests in `tests/test_interop_04.py` from live captures):
  - **Juniper:** a path with no `metric` element (no MED received) read as MED 0, so `med: 0` passed on a route sent without a MED. It now reads as not set, as on FRR and SR Linux, and `med: 0` fails on it.
  - **Arista EOS:** cEOS 4.36.3M prints `"med": 0` for a path received with no MED, and no field of its output tells the two apart. A `med: 0` check on EOS is now refused before the lab boots (exit `2`: "EOS output cannot tell MED 0 from no MED"), and a MED that reads 0 is reported as not set. A non-zero MED is checked as before.
  - **Arista EOS AS sets** are read in the reference form: cEOS prints `{65004 65006}`, which is now `{65004,65006}` as on every other driver, so the same `as_path` check passes or fails the same way on every platform.
- **A route the import policy rejected is never received, and a hidden route never shrinks a prefix count** (0.4 interop test, run 2, live mixed-vendor labs; tests in `tests/test_interop_04_run2.py` and `tests/test_interop_04_fixes.py`):
  - **SR Linux** keeps a route its import policy rejected in the BGP local RIB (`invalid-reason: {rejected-route: true}`), and the driver counted it as a received path: `route ... protocol: bgp active: false` passed on it ("present via bgp (not selected)") and `bgp_route present: false` failed, where FRR, EOS and Junos keep no such path. It is now left out, as on every other driver, so `present: false` passes and `active: false` doesn't; and a failure no longer blames an unreachable next hop for it. A path invalid for any other reason is an error until the driver reads that reason, never a verdict.
  - **Juniper:** `bgp_prefixes` read Junos's accepted count, which also leaves out a received route Junos hid for an unusable next hop: 206 received, 205 accepted, so `max: 205` and `exact: 205` passed where the reference count (received minus rejected by import policy, as FRR, SR Linux and EOS count) is 206. When Junos hides routes from a peer, the driver now reads their reasons (`show route receive-protocol bgp <peer> hidden extensive`, captured live) and subtracts only those rejected by import policy. A hidden route with any other reason, or none, leaves the count a range from accepted to received: a bound passes or fails only when the whole range agrees, and otherwise the check fails with "can't tell whether the bound holds" (an error when the hidden routes couldn't be read at all); `netdryrun record` writes no count for such a neighbor.
- **A repeated key in device JSON is never "the last one wins".** Junos repeats `protocol-nh` inside one route entry (live captures), and plain JSON parsing kept only the last copy, which a next-hop check reads. Junos's repeats are now joined, and several different next hops with none selected is an error; every other driver refuses a repeated key (none of their captures has one).
- **A topology `exec:` command that fails is an error**, on every platform (0.4 multi-vendor audit): containerlab only logs it and exits 0, so the node ran without what the command configured (live: a `vtysh` line FRR rejected). A JSON startup config SR Linux rejects is an error too: the deploy succeeds and SR Linux runs without it (live), so Netdryrun reads its log. Under `netdryrun check` (a lab it didn't deploy) SR Linux and SONiC say `not verified`, and a node without a routing driver says `not verified (no routing driver)`.
- **Startup config a NOS rejected is never a pass, on Arista cEOS, SR Linux and SONiC too** (was scheduled for 0.4 in 0.3.3's limits). cEOS skips a startup-config line it rejects and loads the rest, like FRR: after the checks, Netdryrun reads `show startup-config errors` (captured live on cEOS 4.36.3M), and a listed line, or output it can't account for, makes the run an error (exit `2`) naming the line. SR Linux applies its startup config as one commit at deploy, and containerlab's deploy fails on a line that doesn't parse or a commit that fails (live, 26.7.2), so a running node ran all of it. SONiC (docker-sonic-vs) has no startup config: its `setup:` commands are checked; a config file bound into a SONiC node is an error. `environment.nodes.<node>.config_load` says `clean` or the lines; Juniper (beta) says `not verified on junos`.
- **`verify` compares each FRR node's running config.** Config that acts only on routes or events the lab never produces (a prefix-list for prefixes the lab doesn't carry, `maximum-prefix`, dampening, timers, BFD, a password, `no neighbor X send-community`) used to change nothing observable and ship under NO BEHAVIOR CHANGE. Now NO BEHAVIOR CHANGE needs identical running configs; a config change with no observable effect fails ("this change has no observable effect in the lab; test it with checks"), unless the new intent line `config_change_on: [nodes]` declares it; and every approval lists each changed config line, with its section headers, under "not tested if the lab doesn't exercise them" (`untested_config` in the report and the MCP result, and `untested_config_lines` in the PR comment header).
- **Conditional advertisement delays the snapshot** (gauntlet S2): where a node has an `advertise-map`, `--settle` stretches past `bgp conditional-advertisement timer` (60 s by default) plus 2 s, so a change it makes can't land after two identical snapshots.
- **`verify` reads each side's config load the way `run` does (0.3.3).** A changed line FRR rejected on the after side would read as no change at all; it is now exit code `2` on that side, naming the node and the line, from the same reading of the boot log as `run`. `environment.nodes.<node>.config_load` (and the MCP result's `tested.nodes`) records each node's load: `clean`, why it didn't load as written, or `not verified on <driver>` (Juniper for now), or `not verified (no routing driver)`.
- **What ran is named:** each node's image digest and the NOS version it reports are in the report (`environment.nodes`) and in the MCP result's `tested.nodes` (FRR reads its version; other drivers say null until their output is captured).
- **The Action refuses a PR that changes the checks and the configs together** in `mode: run` (it would grade its own change), before any lab boots, unless `allow-check-edit: true`, which a workflow sets only where branch protection requires a code-owner review of `netdryrun.yml`. Like `mode: verify`, it judges the PR merged into the base branch.

### Fixes

- **A link-local `next_hop` in a `bgp_route` check is refused.** Devices report it without its interface and two sessions can share one, so a path through the other session matched. Found by the 0.3.3 delta review.
- **A run on an FRR lab that skipped a config line is an error, never a pass.** FRR loads its config line by line at boot and skips a line it rejects (a typo such as `default-orignate`, an incomplete command); 0.3.2 ran the checks on the lab without it, so a run could pass on a change that never loaded. After the checks, Netdryrun now reads every FRR node's boot log, and any rejected line makes the run `error` (exit 2), naming the node, line and reason. A daemon can complain about a line and still apply it (bgpd answers `bgp graceful-restart` with "Failure to communicate" on FRR 10.4.1). So such a line doesn't count when line N of the node's `frr.conf` is that line and that daemon's own running config (`vtysh -d <daemon>`) has it under the same headers at every depth (`router bgp`, VRF, address family, `vni`), at least as many times as the file does, and has the line's whole block as written. A refused header line (`vni 10`, `address-family ...`) always counts. Every other kind of rejection always counts, and so does any line when the running config or `frr.conf` can't be read. A boot log that can't be read, or that shows no sign of a config load, is an error too. Nodes whose driver can't be detected are read as well, and only the current boot counts. Advisory: `advisories/0.3.2-rejected-config`. Not yet checked on Arista cEOS, SR Linux or SONiC startup config (config applied with `setup:` commands is): a documented limit, fix scheduled for 0.4.
- **A path with no MED attribute no longer passes `med: 0`** (FRR, EOS, SR Linux). Its MED was read as 0, but with `bgp bestpath med missing-as-worst` a missing MED is the worst, not 0. The MED of such a path is now unknown, so any `med` check fails on it and says `MED is not set`. Found by a Grok review.
- **A link-local neighbor shared by several sessions is never evaluated** (FRR, SR Linux, EOS). Neighbors such as `fe80::1%eth1` and `fe80::1%eth2` share one key, so one session's state or prefix count answered for the other: a down session could hide behind an up one, a `state: down` check could pass while one was up, and a `max` count could be read from the wrong session. A `bgp_session` or `bgp_prefixes` check on such a key now says it is ambiguous and is not evaluated (never a pass); check a global address instead. `record` leaves such a neighbor out with an `INCOMPLETE BASELINE` line. Found by the 0.3.3 cross-platform and delta reviews.
- **Every SR Linux BGP route type counts as BGP** (`bgp-evpn`, `bgp-vpn`, `bgp-label`, ...), so a `protocol: bgp` check, and a `present: false` guard, see a default route imported through EVPN or L3VPN.
- **EOS `Idle(Admin)` reads as `idle`** (EOS prints no space before the reason), so `state: idle` matches an admin-down peer.
- **`record` says when a link has no address where it is read** (SONiC keeps it on `EthernetN`, SR Linux on `e1-Y.0`), with an `INCOMPLETE BASELINE` line, instead of writing no guard silently.
- **A route check on FRR never passes on a graceful-restart stale path.** While a peer restarts, bgpd keeps its paths marked stale until it re-sends them or the stale timer ends; a `route` or `bgp_route` check that sees one now reads it as not settled (not evaluated, never a pass), whether it expects the route present or absent. Found by the 0.3.3 cross-platform review.
- **Known limits stated**, with the mitigation and a fix scheduled for 0.4, in the advisory, the config and `record` references and the compatibility matrix: on SR Linux, EOS and SONiC a graceful-restart stale path still counts as present; SR Linux prefix counts include routes dropped by loop detection; `record` snapshots the default VRF only.

VS Code's key is `servers`, not `mcpServers`; Codex CLI's 60-second default tool timeout is shorter than a dry run, so the page raises it or points to `start_run`.
- **The pull-request path for agents without Docker.** `netdryrun run --verdict FILE` (and `check`) writes the agent result, the same `netdryrun.mcp-result/v1` object the MCP tools return, with the files tested. The GitHub Action writes it (`verdict-report`, default `netdryrun-verdict.json`) and uploads it with the reports, and its PR comment now starts with a fixed header: a `<!-- netdryrun-verdict: {...} -->` line with the status, verdict and counts as JSON, then the verdict in words. The header is held to the run's checked exit code: a missing or contradicting result reads `error`. New guide: [AI agents without Docker](https://netdryrun.com/guides/agent-pr/).
- **An asynchronous MCP shape.** `start_run` returns at once with a `run_id` and `status: running` (no verdict), and `get_result` polls it until the run finishes; the finished result is exactly `dry_run`'s, with its `run_id` (or a setup error, `status: error`, if the run stopped on an internal error). A dry run takes about 60–120 s, longer than some clients wait for one tool call (Codex CLI's default per-tool timeout is 60 s). A config error or a path outside `NETDRYRUN_MCP_ROOT` is answered at once; a run that stops on an internal error ends as `status: error`, never stuck at `running`. Runs live in the server process. The pending shape, `run_pending`, is in the result schema. `dry_run` is unchanged.

## 0.3.2 (2026-10-28)

The agent contract: what an AI agent needs to choose Netdryrun, read its result and act on it safely. Tool names and parameters are unchanged.

### Breaking change for agents: the pass verdict is renamed

- **`SAFE TO PROCEED` is now `CHECKS PASSED (only what the checks cover)`.** A pass covers only what the checks look at; a change that breaks something no check covers passes too, so the verdict no longer says "safe". Wording like "safe to proceed" is kept for a planned before/after comparison verdict that passes only when a change shows no undeclared differences ([verdict spec](https://netdryrun.com/spec/verdict-v1/)).
- **Who is affected:** an agent, prompt, `AGENTS.md` rule or script that matched the text `SAFE TO PROCEED` in an MCP result. It will no longer see that text, so it treats every pass as not-a-pass (fail closed, never the other way).
- **Migration:** decide on the `status` field (`passed`, `failed`, `inconclusive`, `error`), the enum the verdict is mapped from, not on the verdict text; or match the new string exactly. Update `AGENTS.md` lines that say "only if the verdict is SAFE TO PROCEED" to "only if `status` is `passed`" ([snippet](https://netdryrun.com/ai-agents/#paste-this-into-your-network-repositorys-agentsmd)). The CLI, its exit codes, the JSON report and the GitHub Action are unchanged.

### Added

- **A typed result for the MCP tools.** The results of `dry_run` and `run_checks` are defined by a published JSON Schema, [`mcp-result-v1.json`](https://netdryrun.com/schemas/mcp-result-v1.json), which also covers `validate`, `check_types` and `record_baseline` errors. Results carry `"schema": "netdryrun.mcp-result/v1"`. A test validates the results of real lab runs, and of the tools called over stdio, against it.
- **The verdict strings are frozen**: `CHECKS PASSED (only what the checks cover)`, `DO NOT APPLY THIS CHANGE` and `INCONCLUSIVE: the lab did not reach a testable state; this says nothing about your change. Do not apply it until a run passes.` They never change within v1.
- **Failed results explain themselves.** A new `failures` list has one entry per failed check: the check name, its node, the one-line `reason`, a short `evidence` excerpt (the command, its exit code and the start of its output, one line, at most 200 characters) and one read-only `next_diagnostic` command for that node in its own CLI, such as `docker exec clab-lab-r1 vtysh -c 'show ip route 0.0.0.0/0'`. Run it on a lab kept with `keep_lab: true`.
- **An agent skill**, `skills/netdryrun/SKILL.md`, installable from the repository's git URL: before applying a routing change, dry-run it; paste the verdict; stop on inconclusive; never write or weaken checks to make a change pass; use `record_baseline` when there are no checks.
- **An AGENTS.md snippet** for your own network repositories, on the [AI agents](https://netdryrun.com/ai-agents/#paste-this-into-your-network-repositorys-agentsmd) page.
- **Results name what they tested.** `dry_run` and `run_checks` results carry `tested`: a sha256 of `netdryrun.yml`, the topology and every config file the topology binds or loads as a startup config (shared files in another folder included), read before the run, plus `lab_deployed_by_this_run` (false for `run_checks`, which tests a lab that was already running) and `complete`. A pasted verdict can now be tied to the exact files it ran; in the agent evaluation, a run on the unedited folder was read as a run of the change (ticket T06). `tested.config` is the `netdryrun.yml` that ran. Files in topology groups, licences and env files are listed too; with `NETDRYRUN_MCP_ROOT` set, files outside it are not read, and a file named with `~`, `${VAR}` or a URL (containerlab resolves those) is not read either; `complete` is then false. The field is in the result schema and, as an optional field, in the verdict spec.
- **Network Change Verdict v1**, an open spec page for the `netdryrun.report/v1` format, so other tools can emit the same verdict document: [spec/verdict-v1](https://netdryrun.com/spec/verdict-v1/).

### Changed

- **MCP tool descriptions** now all state when to use the tool (before proposing or applying a routing or policy change), that ping is not a test, the runtime (about 60–120 s per dry run), the requirements (Linux or WSL2, Docker and containerlab with root-equivalent rights; not macOS, not sandboxes without Docker-in-Docker), that inconclusive means stop with at most one retry, and never to invent or weaken checks but to call `record_baseline` when none exist. `dry_run` is named the primary tool.
- **The `dry_run` description carries the open-model evaluation's interface fixes**, since small models read only the tool text: write the change into the configs first (a run on the unedited folder tests today's config, not your change); on a ticket that adds behaviour the first run is expected to fail the new checks, and a failed run means fix the config and run again, not stop; for a change claimed to alter nothing, a pass is not proof: read the diff and compare with a `record_baseline` of the unchanged configs. Every tool description now also says that status `error` or `inconclusive` is a setup problem that says nothing about the change.
- **The MCP Registry description** (`server.json`) is now the opening of the one-sentence definition; the registry caps it at 100 characters.

### Fixes

- **A relative path given to an MCP tool is read from `NETDRYRUN_MCP_ROOT`, not only from the server's own working directory.** An agent that passed `netdryrun.yml` was told the file was "outside NETDRYRUN_MCP_ROOT" although it was inside it. With `NETDRYRUN_MCP_ROOT` set to one folder, a relative path is now read from that folder; with no root or several, the tool refuses it and asks for an absolute path, with an example. If the server's working directory holds a different file at the same relative path (an agent's worktree inside the root, say), the tool refuses it too rather than guess which file the agent edited; if only the working directory has it, that file is used, as before. The root check still applies after resolving, so `../` can't step outside. This holds for `dry_run`, `run_checks`, `validate`, `record_baseline` and the report resource.
- **A lab that never reached a testable state is inconclusive (exit 3) with failure scenarios in the file too.** With `bgpd` off on every node, 0.3.1 ran the main checks, then stopped at the first scenario with exit 2 ("could not read BGP state on r1"); the same file without scenarios exited 3. Now, when the main checks already show the lab never gave usable state and every node a scenario faults or checks is one of the nodes that never gave state, the scenarios are skipped (no fault is applied) and the run ends inconclusive. A scenario on a node that did give state still runs, so a real failure there is still exit 1. It is never a pass, and a scenario whose BGP state can't be read after main checks that did read state still stops the run with exit 2 naming the node, as in 0.3.1.
- **A lab where no node ever gave routing state is inconclusive (exit 3), not failed or error.** With `bgpd` off on every router (the agent evaluation's broken-lab ticket, T10), 0.3.1 returned `error` at the failure scenario, or `failed` without one, and a small model read that as a verdict on the change. A ping with no replies on a node no longer stops it from counting as one that never gave state, when the node's route or `bgp_route` checks never got a readable answer on any sample: a ping can't show that a node gave routing state. Every other condition of the inconclusive rule is unchanged (nothing passed anywhere, no post-convergence check failed with readable state), a readable routing table without the route is still a finding, and it is never a pass. Known limit, as before: a change that stops the routing daemon on every node looks the same and is reported inconclusive.
- **A router whose BGP config never loaded no longer passes its leak guards.** In 0.3.1 a node that answered with no BGP neighbors at all was released at the convergence gate's cap with a warning, so `present: false`, prefix-count `max` and attribute checks could pass on its empty table (a limit stated in the 0.3.0 advisory). Now, when the file has a BGP check on that node (`bgp_session`, `bgp_prefixes`, `bgp_route`, or a `route` with `protocol: bgp`), its post-convergence checks fail at the cap as `not evaluated: <node> reported no BGP neighbors by the cap`, every sample unready; the run is inconclusive when nothing anywhere gave usable state. A node with no BGP check anywhere in the file (static routing) still goes ahead with the warning. Found by the multi-vendor AI audit (Grok). Still a limit, stated in the advisory and the config reference: a peer with a long advertisement interval can deliver a route after a negative check was released; raise `--settle` and `--hold` above it (0.4 will read the interval and extend the settle window).
- **The MCP server writes `netdryrun-report.json` to a new file and renames it into place.** A hard link at that name (to a file elsewhere) is replaced, not written through; 0.3.1 already replaced a symbolic link. Found by the multi-vendor AI audit.
- **An IPv6 scope in a check address must be an interface name.** `target: "fe80::1%eth1"` loads as before; text after `%` with spaces, newlines or other characters is now a config error (exit 2). Python's address parser accepted any text there, and the address reaches device CLI commands, including the MCP result's `next_diagnostic`, so a crafted `netdryrun.yml` could add lines to them.
- **GitHub Action:** the job is green only when the run exited `0` **and** its report says `passed`. Before, a run that exited `0` with a report that said otherwise, or with no report, set the `status` output to `error` but left the job green. No released version is known to produce that combination; this closes it for any future bug. Found by a new test that runs one report through the CLI, the MCP server and the Action and requires the same verdict from each.

## 0.3.1 (2026-10-28)

**Upgrading from 0.3.0, read this first:**
- **Why:** 0.3.0 could report `passed` without testing what a file said (the paths are listed under Fixes, with rerunnable files in [the advisory](advisories/0.3.0-false-pass/README.md)), and had the injection paths listed under Security.
- **Pins:** `pip install netdryrun==0.3.0` still installs 0.3.0, and `uses: netdryrun/netdryrun@v0.3.0` keeps running 0.3.0 until you change it to `@v0.3.1`.
- **Run `netdryrun validate`.** Files that 0.3.0 accepted can now exit 2: quoted booleans, an unknown `afi` or `protocol`, duplicate keys, `min: 0` on its own, `vrf: all`, a `hold` with no effect, a misspelled top-level or `nodes` key, `afi: evpn` on EOS or SR Linux. Each of those was a check that didn't test what it said. Validate catches config problems only, so also rerun a representative lab.
- **Some verdicts change with no config edit:** received paths count as present even when not selected; SR Linux's own routes no longer fail `present: false`; best-path attribute checks wait for BGP convergence; `ping` with `expect: failure` passes when the destination is unreachable; a scenario session that the fault takes down indirectly (iBGP over a path behind the cut) needs a `bgp_session` check with `state: down`, or the scenario's negative checks fail as not evaluated.
- **Exit codes:** 0 passed, 1 checks failed, 2 not tested (config or lab problem, including "the fault did not take effect" and a report that couldn't be written), 3 inconclusive. A lab of the same name that is already running is refused and left alone. The Action deletes report files already in the workspace before it runs.

### Security

- **Names that reach a device command are checked.** `vrf` names are restricted to letters, digits and `. _ : -` (at most 64 characters), and `link_down` interface names to Linux interface names (at most 15 letters, digits and `. _ @ -`), before they go into `vtysh -c`, `sr_cli`, `Cli -c` or `ip link`. Before, a `netdryrun.yml` with a newline or a pipe in one of these names could run a second command inside a lab node. Configs that used other characters now fail validation (exit code `2`).
- **SR Linux:** the `attr-id` and the neighbor address read from device output are checked before they go back into a CLI command, so output from a lab node can't add to that command.
- **Markdown summary and PR comment are inert.** HTML, links, images, `@mentions` and `#123` references from configs or device output are escaped, and code blocks are sized so device output can't close them. Before, text from a lab could forge content in a PR comment or ping people.
- **`netdryrun record`:** warnings that quote device output stay on one YAML comment line, so device output can't add keys to the recorded baseline.
- **MCP server:** a new optional `NETDRYRUN_MCP_ROOT` confines the configs, the labs they point to, topologies and report reads to the listed folders (0.3.0 had no such setting and ignores the variable). `detail` and `error` in tool results are flattened to one line and capped (300 and 1,000 characters). The evidence file is never written through a planted symlink. `record_baseline`'s `wait_seconds` is bounded (0 to 600).
- **GitHub Action:** report files already in the workspace (committed in the PR, or left by an earlier run on a self-hosted runner) are deleted before the run, and the `status` output is `error` unless the report matches the run's own exit code, so a PR can't fake a pass with a committed report. The `inconclusive-reason` output is one line without quotes, backslashes, `$` or backticks.

Impact: in the Action, `netdryrun.yml` comes from the pull request, so on 0.3.0 a pull request could put a second command (through `vrf` or `link_down`) into a privileged lab container, or forge the PR comment. 0.3.1 allowlists those fields and escapes the comment. MCP stays able to reach labs outside the folders you meant until you set `NETDRYRUN_MCP_ROOT`; put it in your agent's MCP configuration.

### Fixes

- **`present: false` on SR Linux no longer fails on the router's own routes.** SR Linux lists its own static and interface routes in its BGP RIB as locally originated paths (neighbor `0.0.0.0`), whether or not an export policy advertises them; this was seen live on SR Linux 26.7.2. So on a router with a static default, `bgp_route` with `present: false` and `route` with `protocol: bgp, present: false` for `0.0.0.0/0` failed even when no peer sent a default. Those rows no longer count for `present: false`, and the `route` check no longer reports them as BGP routes. Best-path checks (`bgp_route` with attributes) still read them, so asserting `as_path: ""` on a router's own route works as before. Found while building the new `examples/srl-hidden-leak` lab.
- **The Markdown summary and PR comment of a big lab.** A GitHub comment holds at most 65,536 characters, and the summary listed every check (about 90 characters each), so above roughly 700 checks (a recorded 20-node lab gets there) the Action's `pr-comment` was rejected with a misleading permissions warning. The table now stops before the limit, failures first, and says how many checks it left out; the JSON and JUnit reports still have every check. Found by a 20-node scale test.

A pre-launch audit and a cold code review looked for ways a run could say `passed` without testing what the file says. The fixes below close the paths they found; the limits that remain are in [the advisory](advisories/0.3.0-false-pass/README.md#limits-that-remain-in-031). Some configs that 0.3.0 accepted are now refused (exit code `2`); each of those was a check that didn't test what it said. Run `netdryrun validate` after upgrading.

Fixes for runs that could pass without testing what they said:

- **A misspelled key outside a check no longer drops it silently.** 0.3.0 already refused unknown keys inside a check or a scenario, but ignored them at the top level (a misspelled `checks:` block, for example a list of leak guards under `chekcs:`, never ran), under `nodes.<node>` (a misspelled `driver` was ignored), and inside `node_isolated`. Unknown keys are now errors at every level, with a "did you mean" suggestion.
- **Quoted booleans no longer flip a check.** `present` and `active` must be unquoted `true` or `false`; `"false"`, `0`, `null` and empty values are errors. Before, `present: "false"` was read as true.
- **An unknown `afi` no longer reads as 0 prefixes.** `afi` must be `ipv4-unicast`, `ipv6-unicast` or `evpn`. Any other family counted 0 prefixes, which passes `max` and `exact: 0`.
- **An unknown `protocol` no longer matches nothing.** `protocol` must be one of the names the drivers report (the list is in the [reference](https://netdryrun.com/reference/config/#protocol-names)); `ebgp`, `ibgp`, `direct` and similar get a suggestion. Before, other names were passed through, matched no route, and silently passed `present: false`.
- **Duplicate YAML keys are errors**, in `netdryrun.yml` and in the topology. Plain YAML keeps the last one, so a second `checks:` block or a repeated `present:` silently replaced the first.
- **`min: 0` on its own is refused** (it always passes), and **`hold` on a check where it has no effect is an error** instead of being ignored.
- **`vrf: all` is refused.** Devices answer it keyed by each VRF's name, which the drivers read as "no routes".
- **`afi: evpn` on Arista EOS and SR Linux is refused before the lab deploys.** Those drivers read only the IPv4 and IPv6 unicast counts (SR Linux has no received-routes counter for EVPN, so the driver skipped the family), so an EVPN count always read 0 and passed `max` and `exact: 0`. FRR and SONiC read the EVPN count from the router's BGP summary; a family a neighbor doesn't carry counts as 0 received prefixes.
- **Scenario checks are never judged on the state from before the fault.** After taking links down, a scenario waits until the BGP sessions over those links are down on both ends (capped at the largest timeout of its checks), then settles; positive checks must pass on 2 consecutive samples and then hold for `--hold`. If the fault never shows, the run ends with exit code `2`, "the fault did not take effect". Before, a scenario's positive checks could pass on the network as it was before the failure.
- **Negative checks wait for every BGP session on their node.** A post-convergence check starts only once every configured BGP neighbor on its node is established with stable prefix counts (neighbors a `bgp_session` check expects down don't count), capped at its timeout. If a session never comes up, the check fails as "not evaluated" and names it. Before, a leak arriving over a session nobody checked could come after the check had already passed.
- **`bgp_route` attribute checks are judged after convergence.** A `bgp_route` that asserts any best-path attribute (`next_hop`, `as_path`, `as_path_regex`, `local_pref`, `med`, `communities`, `without_communities`) is now a post-convergence check: it waits for every BGP session on its node, the settle delay, and must hold for `--hold`. Before, all of these except `without_communities` passed on 2 early samples, so they could pass on a temporary best path that changed when a slower session came up. A `bgp_route` with no attributes (the best path exists) is still a positive check. `hold` is now accepted on these checks.
- **A node with no BGP neighbors at all is not converged.** The BGP gate released at once when a node reported no neighbors, the answer of a node whose BGP config isn't applied yet, so a leak that arrived later passed `present: false`. The gate now keeps waiting, up to its cap (the check's `timeout`). If the node still reports no neighbors then, its post-convergence checks run with a warning in their result that they were evaluated without BGP convergence; the verdict is unchanged. A node without BGP therefore adds one `timeout` of waiting to its post-convergence checks.
- **A scenario whose BGP state can't be read before the fault stops with exit code `2`.** Before taking links down, a scenario reads the BGP sessions on both ends of each link (and the downed interfaces' addresses) to know which sessions the fault must bring down. A read that failed counted as "no sessions", so the scenario skipped the wait for the fault to take effect and was judged after the settle and hold only. Now the run ends with a one-line error naming the node, before any link goes down. "No BGP session runs over the downed links" is logged only when the state was read and shows none (a node without a driver, or a VRF the node says it doesn't have, still counts as none).
- **Post-convergence checks in a scenario wait for the BGP gate.** Inside a scenario, a post-convergence check (a leak guard, a `max` prefix count) now waits, as at the top level, until every BGP session on its node is up with stable prefix counts, capped at its timeout. Sessions over the links the scenario took down don't count, nor do sessions a `bgp_session` check expects down. Before, these checks were judged right after the settle delay; for `inject_routes`, the run had only waited for the prefixes to be in the injecting node's own table, so a leak still on its way to the node under test could pass. A peer with a long advertisement interval can still delay the routes beyond the gate (documented); a session the fault takes down indirectly (iBGP over a downed path) needs a `bgp_session` check with `state: down` in the scenario, or the checks fail as "not evaluated".
- **Drivers never read an error as "nothing".** A VRF that doesn't exist is an error on every driver (FRR and SONiC confirm it with `show vrf`, SR Linux with the network-instance's oper-state, Arista EOS by its `vrfs` map), and so are a failed command and output the parser doesn't recognize (empty output, a wrong type, a renamed field). Before, some of these read as "no routes" or "no prefixes", which passes `present: false` and `max`. Arista EOS no longer ignores a failed `show ipv6 bgp summary`, and SR Linux no longer ignores a failed neighbor local-preference lookup.
- **Received paths count as present on every driver**, valid or not, selected or not: SR Linux no longer skips invalid paths, and FRR's `route` check now also reads the BGP table. The router's own paths (network statements, redistribution) don't count as received.

Other fixes:

- **Number ranges.** `timeout` and `hold` must be positive and at most 86400 seconds; ping `count` 1 to 1000; `min_replies` 1 to `count`, and not with `expect: failure`. Before, `count: 0` and `min_replies: 0` were accepted, the top-level `timeout` was not checked, and `.inf` passed as a timeout.
- **`ping` with `expect: failure` passes when the destination is unreachable.** With no route at all, ping prints "Network unreachable", "No route to host" or "Destination unreachable" and sends nothing; that was reported as "ping did not run" and failed.
- **SIGTERM and SIGHUP clean up like Ctrl-C.** The lab is destroyed (unless `--keep`), a `--json` report with `status: error` is written, and the exit code is 128 plus the signal: 143 for SIGTERM, 129 for SIGHUP, 130 for SIGINT. A second signal can't interrupt the cleanup. The MCP server destroys the labs it is running when it gets SIGTERM.
- **Crashes and bad input exit 2 with one line**, never a traceback or exit code `1` ("checks failed"): bad YAML (with its line and column), wrong types, bad topologies, a negative `--settle` or `--hold`, and internal errors. `--debug` or `NETDRYRUN_DEBUG=1` prints the traceback. With `--json`, an error report is written, including for a config error.
- **A report that can't be written after the verdict exits 2 with a clear line.** If `--json`, `--markdown`, `--junit` or the step summary can't be written (an unwritable path, a missing folder), every other report is still written, and each failure prints `could not write <path>: <reason>; the verdict was <status>`. The exit code is `2`: the evidence asked for is missing. Before, the first failure was reported as an internal error and the remaining reports were not written.
- **A lab with the same name already running is refused** with exit code `2`, and left alone, instead of being redeployed and then destroyed. Two runs of the same lab started together on one host are refused by a lock. A run that never deployed never destroys anything: an error found before deploying (a typo in a node name) no longer destroys a lab you kept running with `--keep`.
- **`netdryrun validate` reads the topology** and makes the checks `run` makes before deploying, without Docker or containerlab: unknown nodes, nodes without a driver, keys a node's driver can't read, `inject_routes` on a non-FRR node, and link faults on SR Linux nodes. The MCP `validate` tool does the same. Before, `validate` said `OK` to a file that `run` then refused.
- **The Markdown summary and PR comment show the proof.** The evidence for a failed check lists every command of its final sample (a route check reads the routing table and the BGP table), and the excerpt keeps the lines that say which route the device selected, with their protocol. Before, the excerpt of a "not selected" leak stopped before the `selected` field.
- The MCP `check_types` tool lists `hold` among the keys every check accepts.
- **Releases carry signed build provenance** (Sigstore, SLSA): verify a downloaded wheel with `gh attestation verify <file> -R netdryrun/netdryrun`; the bundle is also attached to each GitHub release.
- **Install instructions use `pipx install netdryrun`** (or `uv tool install netdryrun`). Ubuntu 24.04 and Debian 12 refuse a plain `pip install` outside a virtualenv, so the old first command failed there.

## 0.3.0 (2026-10-27)

- **Friendlier long waits:** the deploy line says it usually takes 30-90 s (longer when images are pulled), and Ctrl+C prints "Interrupted: no verdict" with exit code 130 instead of a Python traceback. The lab is still cleaned up. Found on the first real Codespaces run.
- **New check type `bgp_route`: attributes of the BGP best path.** `communities` (must carry all; standard, large and well-known names), `without_communities` (must carry none), `as_path` (exact) and `as_path_regex`, `local_pref`, `med` and `next_hop`, plus `present: false` (no path at all in the BGP table). Many real policy bugs are attribute-level: a route that is still there but lost its community, got the wrong local preference, or now goes the long way. Works on FRR, SR Linux, Arista EOS and SONiC; every parser is tested against output captured from live labs, and the examples gained `bgp_route` checks. A key a driver can't read stops the run before deploying with "not supported on `<driver>`" (today every driver reads every key). `netdryrun record --attributes` (and `record_baseline(attributes=true)`) also pins each BGP route's AS path, local preference and communities.
- **New status `inconclusive` (exit code `3`)**: checks failed, but the lab never reached a testable state, so the run says nothing about the change. The rules are conservative: nothing passed on any sample anywhere in the run, and every failing node never returned usable BGP state (its CLI never answered, or BGP had no neighbors at all). A configured session that is down is always `failed`, because an ASN typo looks the same as a slow lab. The JSON report gains `inconclusive_reason` and `"unready": true` on such samples; the Markdown summary and PR comment say so; JUnit reports those checks as errors, not failures; the MCP verdict is `INCONCLUSIVE: the lab did not reach a testable state; this says nothing about your change. Do not apply it until a run passes.`; the GitHub Action reports `status: inconclusive` and a new `inconclusive-reason` output, and still fails the job. Rules: [CLI and reports](https://netdryrun.com/reference/cli/#when-a-run-is-inconclusive).
- **Report schema `netdryrun.report/v1` stays v1**: this release only adds things (the `inconclusive` status value and the `inconclusive_reason` field, plus `unready` in history samples). A consumer that only knows `passed`, `failed` and `error` should treat any other status as not passed.
- A `bgp_session` or `bgp_prefixes` check on a node with no BGP neighbors at all now says so ("no BGP neighbors at all on this node") instead of "seen: none".
- **`netdryrun feedback`** opens a short GitHub feedback form, prefilled with only the version and platform; nothing is sent until you submit it. After an interactive run (not in CI), one line points to it. New **design partners** page: free help testing one real change, in exchange for feedback.
- **Try it in your browser:** a devcontainer (`.devcontainer/`, containerlab's Docker-in-Docker image with containerlab 0.81.1, Netdryrun installed from the checkout, FRR image pre-pulled) and an "Open in GitHub Codespaces" badge, so the agent demo runs with nothing installed.
- **Agent demo** (`examples/agent-demo`): a ticket, a tempting change that passes the ticket checks but leaks routes (rejected), and the proper fix (accepted). `demo.sh` replays it and checks that attempt 1 fails only on the leak guards; CI runs it on pushes to `main` and on pull requests.
- MCP server reports its version and website in `serverInfo`.

## 0.2.0 (2026-10-27)

- **Fix: a change that breaks a baseline check no longer turns a scenario run into `error`.** The recovery check after a scenario now only requires the checks that passed before it; a network that really doesn't recover is reported as failed `[after <scenario>] recovers: ...` checks (exit 1), not a lab error (exit 2). Found by running the edge-guard pack against the Verdict Corpus.
- **SONiC driver** (docker-sonic-vs): sessions, prefix counts, routes, ping, record, failure scenarios. New `nodes.<node>.setup` key runs post-boot configuration commands (retried until the NOS is ready). New example: `examples/sonic-frr`.
- **Arista EOS driver** (cEOS-lab, bring your own image): sessions, prefix counts, routes (routing table + BGP table), ping, record, failure scenarios. New example: `examples/arista-frr`.
- **Leak detection fixed on SR Linux and Arista**: a leaked BGP route that is received but not installed (it lost to a static or local route) only appears in the BGP table on those platforms. Both drivers now read it, so `present: false` fails as it should. Found by live leak tests; regression tests use real captured output.
- **`netdryrun record`**: snapshot a known-good running lab into a `netdryrun.yml` baseline (BGP sessions, exact prefix counts, BGP routes), so you don't write checks by hand.
- **Failure scenarios**: `scenarios:` with `link_down` and `node_isolated` faults. Links are always restored, and the network settles before the next scenario.
- **Faster runs**: positive checks are polled together against one shared convergence window, and post-convergence checks hold together. A badly broken change now costs about one timeout instead of one per failing check (the corpus runs 2-3x faster).
- **GitHub Action `pr-comment: true`**: one pull-request comment with the verdict and the evidence for each failed check, updated in place on every push.
- **PR-ready evidence**: the Markdown summary now includes the exact command and the relevant raw output for each failed check.
- **`state: down`** for `bgp_session`: any state except established.
- **`active: false`** for present routes: accept a route that is in the table but not selected.
- **MCP built in**: `netdryrun mcp` starts the server (no extra install). New `record_baseline` tool. Listed in the official MCP Registry metadata (`server.json`).
- **Network Change Verdict Corpus**: 30 pre-registered cases comparing ping-only, session-only and Netdryrun checks, with losses published.

# Oracle spec FP-042-FRR102: `record --deploy` on FRR 10.2.1 stops on a BGP answer with no paths list

Status: **spec only**. A session that is not the fixer writes the oracle from a live capture. The capture waits for
the coordinator's "IPI: renders done" and the hub's ok. The FRR image is free and the lab is small (two or three FRR
nodes).

## The bug (found by the stranger on published 0.4.1)
- **Where:** hq run 42599196181, artifact `unseen-result`, lab `martimy/clab-bgp-frr` at ac5b96c (FRR 10.2.1, BGP
  unnumbered).
- **What happens:** `netdryrun record --deploy` exits 1 with 18 INCOMPLETE BASELINE gaps.
- **For each leaf's own LAN prefix:**
  - `show bgp <afi> unicast <prefix> json` answers `{prefix, version, advertisedTo}`, with no `pathCount` and no
    `paths`;
  - `drivers/frr.py::_path_count` raises `unexpected(... "no pathCount")`.
- **Severity:** it fails safe (no false pass), but it blocks the README "your lab" path on FRR 10.2.

## The judgement this must settle (the false-pass risk)
- The strict parser exists because a path missing from under its count must never read as fewer paths, or as none
  (0.4.1, the Junos fuzz shape).
- **An answer with no paths list may NOT be read as "absent".** `advertisedTo` being present says bgpd is advertising
  the prefix, so a BGP route exists. Reading it as absent would pass `bgp_route present: false` on a route that is
  there.
- **Only two outcomes are allowed:**
  1. **The capture or FRR's source proves where the paths are**, for example another command or flag that lists them
     on 10.2. The driver then reads them there and checks the count. This needs a citation: an FRR 10.2.1 source line
     (bgpd `bgp_route.c`, the JSON branch for a prefix lookup) or the captured output. It never rests on a model's
     memory.
  2. **Otherwise the gap stays, made explicit and actionable.** `record` says:
     - for which prefix bgpd printed no paths;
     - that it is the node's own advertised route (advertisedTo present);
     - what to do: pin it by hand, or use a supported FRR version, if the capture shows which ones list paths.

     It records no guessed attribute, and no `present: false` from it.
